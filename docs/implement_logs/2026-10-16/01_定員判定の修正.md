# 定員判定の修正（ホストが人数に数えられず定員を超えて参加できる問題）

- 実装日: 2026-10-16
- 所要時間: 00:24 〜 00:52（Issue #235 の作成時刻から）
- Issue: [#235 定員判定でホストが数えられず、定員を1人超えて参加できる](https://github.com/motty93/mhp-rooms/issues/235)

## 概要

### 原因

- 部屋作成時に `rooms.current_players` を 0 で作成し、ホストを `room_members` に追加しても加算していなかった。この列の値は「ホストを除いた人数」だった
- 参加判定（`roomRepository.JoinRoom`）は `Room.CanJoin()` → `Room.IsFull()` でこの列を使って満員を判定していた。そのため定員2の部屋（ホスト + 1人で列の値は 1）に3人目が参加できた
- 部屋一覧などの表示は `room_members` の件数（ホスト込み）で出しているため、表示と判定で人数がずれていた

### 修正内容

- `internal/repository/room_repository.go`
  - `CreateRoom`: ホスト分として `current_players = 1` を設定してから作成するようにした
  - `JoinRoom`: 満員判定を `room_members` の active 件数（ホスト込み）で行うようにした。満員なら `ROOM_FULL:満員のため参加できません` を返す。参加後の `current_players` は `activeCount+1` を保存する（相対加算をやめた）
  - `removeMember`（退出・キック共通）: 相対減算をやめ、status 更新後に active 件数を数え直して保存するようにした。本体を `removeMemberTx(tx, ...)` に切り出し、呼び出し元のトランザクション内でも使えるようにした
  - `JoinRoom` のシグネチャを `JoinRoom(roomID, userID, password, leaveCurrentRoom bool)` に変更し、他の部屋からの強制参加の退出を同じトランザクションで行うようにした
- `internal/repository/interfaces.go` / `internal/repository/repository.go`: シグネチャ変更の反映
- `internal/handlers/rooms.go`
  - 部屋作成時の `CurrentPlayers: 0` を削除した（リポジトリ側で設定するため）
  - 参加ハンドラーの事前退出ブロックを削除し、`req.ForceJoin` を `JoinRoom` に渡すようにした
  - `ROOM_FULL:` を `409 Conflict` + `{"error": "ROOM_FULL", "message": "満員のため参加できません"}` に変換する分岐を追加した（`KICKED:` の分岐と同じ書き方）
- `templates/pages/rooms.tmpl` / `static/js/profile.js`: 強制参加の確認ダイアログ経由の参加（`confirmJoinRoom()`）に、409 かつ本文に `ROOM_FULL` を含むときは JSON の `message` を表示する分岐を追加した
- `content/info/2026-10-16-october-update.md`: 10月分の更新情報を新規作成した
- `internal/repository/room_capacity_test.go`: 新規（後述）

## 注意した点・工夫した点

### 満員判定は件数ベースにし、列は毎回数え直す

- 満員判定は `current_players` 列を信用せず、`room_members` の active 件数で行う。判定のたびに `room.CurrentPlayers` へ実件数を代入してから `IsFull()` を使うので、モデルの判定ロジックはそのまま使える
- 列は相対加減算をやめ、参加・退出のたびに数え直した値で上書きする。ずれが蓄積しない
- 既存の稼働中の部屋は列がホスト抜きのまま残っているが、判定が件数ベースなので影響しない。次の参加・退出で正しい値に直る

### 判定の順序

`JoinRoom` の判定順は「キック済み → 参加済み → 解散・締切 → 満員 → パスワード → 他の部屋」にした。

- 参加済みを満員より前にした理由: 満員の部屋に既に参加しているメンバーが再度参加 API を呼んだとき、満員エラーではなく従来どおり `ALREADY_JOINED:` を返し、画面を部屋詳細へ遷移させるため
- 他の部屋のチェックを最後にした理由: 参加できない部屋（満員・パスワード違い）のために「今の部屋から退出して参加しますか？」の確認を出さないため。満員やパスワードの誤りは確認の前に表示される

### 強制参加の退出と参加を同じトランザクションにした

- 以前は、ハンドラーが先に元の部屋から退出させてから `JoinRoom` を呼んでいた。そのため、参加に失敗すると元の部屋だけ失った（パスワード違いでも同様）。満員判定が正確になると「満員の部屋へ強制参加 → 元の部屋だけ失う」が起きやすくなるため、同時に対処した
- `leaveCurrentRoom` が false のときは従来どおり `OTHER_ROOM_ACTIVE:` を返す。true のときは `removeMemberTx` で同じトランザクション内で退出させる（status を left、`left_at`、旧部屋の `current_players` を件数で再計算、`leave` ログ）。参加が失敗するとトランザクションごとロールバックされ、元の部屋に残る
- 他の部屋のチェックの位置は、原子性ではなくエラーの優先順位を決める。ロールバックにより、先頭に置いても元の部屋は残る。ただし先頭だと OTHER_ROOM_ACTIVE が先に返り、上記の確認ダイアログが出てしまうため最後にした

### ROOM_FULL を 409 の JSON で返す

- `KICKED:` / `OTHER_ROOM_ACTIVE:` と同じく、ハンドラーでプレフィックスを見て JSON に変換する。共有リンクの参加ページは応答を `response.json()` で読むため、プレーンテキストの 400 ではなく JSON で返す必要がある
- 「満員のため参加できません」は、リポジトリのエラーメッセージからプレフィックスを除いたものをそのまま表示する

### 未使用コードの削除

- `IncrementRoomPlayerCount` / `DecrementRoomPlayerCount`: 相対加減算をやめたため、実装・インターフェース・委譲メソッドを削除した（呼び出し元は元々なかった）
- `Room.CanJoin()`: 判定をリポジトリで直接行うようになり、参照がなくなったため削除した。コード・テスト・テンプレートに参照が残っていないことを `rg` で確認した。`docs/implement_logs` の過去ログには記述が残るが、過去の記録なので変更していない

## 挙動の変更点

判定順の変更に伴い、次の挙動が変わった。

- 締切済み（`is_closed`）の部屋の参加済みメンバーが参加 API を呼ぶと、従来の 400「ルームに参加できません」ではなく、`ALREADY_JOINED:`（200 + 部屋詳細への redirect）になる
- 強制参加の退出に失敗したときの応答は、従来のハンドラーの 500 から、汎用分岐の 400 に変わる（本文は「現在の部屋からの退出に失敗しました: …」）

## フロントエンドの確認

ROOM_FULL（409 の JSON）を受けたときに `message` を表示できるかを、参加する 3 つの経路で確認した。

- 共有リンクの参加ページ（`templates/pages/room_join.tmpl`）: 409 の JSON は最終の `else` 分岐で `data.message` が表示される。変更不要
- 部屋一覧のモーダル（`templates/pages/rooms.tmpl`）: `joinRoom()` は 409 を `errorData.message` で表示する。変更不要。確認ダイアログ経由の `confirmJoinRoom()` は失敗時に本文をそのまま表示するため、JSON が生で出てしまう。分岐を追加した
- プロフィールのモーダル（`static/js/profile.js`）: `joinRoom` は 409 の `message` を表示する。変更不要。`confirmJoinRoom()` は `rooms.tmpl` と同じ理由で、同じ分岐を追加した

追加した分岐は、既存のパスワードエラーの分岐と同じ書き方にした。

```js
if (response.status === 409 && errorText.includes('ROOM_FULL')) {
  throw new Error(JSON.parse(errorText).message)
}
```

## テスト結果

`internal/repository/room_capacity_test.go` を新規作成した。`recent_activity_test.go` と同じ作り（`gorm.io/driver/sqlite` の `:memory:`、`GetConn` / `Close` / `GetType` を持つテスト用 DB 型、`NewRepository`）で、AutoMigrate は User / GameVersion / Room / RoomMember / RoomLog に絞っている。`TestRoomCapacity` の 10 ケースはすべて成功した。

1. 部屋作成直後の `current_players` は、ホストを含む 1
2. 定員2の部屋で、ホスト + 1人の参加は成功し、3人目は `ROOM_FULL:` で拒否される
3. 退出すると別のユーザーが参加できる。各操作後に `current_players` と active 件数が一致する。退室済みレコードの再アクティブ化も確認した
4. キックで空いた枠に別のユーザーが参加できる。キック済みのユーザーは満員でも `KICKED:` になる
5. 満員の部屋に参加済みのメンバー（ホストを含む）が再度参加すると `ALREADY_JOINED:` になる（`ROOM_FULL:` ではない）
6. `current_players` が古い値（実際は2人なのに 1）でも、3人目は拒否される。その後の退出で列が正しい値に直る
7. 他の部屋に参加中のユーザーが満員の部屋へ強制参加しても、`ROOM_FULL:` になり元の部屋に残る。強制参加でなくても `OTHER_ROOM_ACTIVE:` ではなく `ROOM_FULL:` が返る（判定順の固定）
8. 他の部屋に参加中のユーザーがパスワードを間違えて強制参加しても、パスワードエラーになり元の部屋に残る。正しいパスワードなら移動できる
9. 強制参加に成功すると、元の部屋は left になって人数が再計算され（`leave` ログが残る）、移動先に参加できる
10. 強制参加でなければ、他の部屋に参加中のユーザーは `OTHER_ROOM_ACTIVE:` になり、どちらの部屋も変わらない

### テストの有効性の確認

作業ツリーとは別のコピーで、実装に次の変更を加えてテストが失敗することを確認した（リポジトリには残していない）。

- 修正前の `room_repository.go` に戻す: 当時の 6 ケースがすべて失敗する（列がホストを数えない、定員超過の参加を許す、など）
- 参加済みの判定を満員チェックの後ろへ移す: ケース 5 が失敗する
- 強制参加の退出をトランザクションの外で先に行う（旧ハンドラー相当）: ケース 7・8 が失敗する（元の部屋が left になる）
- 他の部屋のチェックを先頭に戻す: ケース 7・8 が失敗する（`ROOM_FULL:` やパスワードエラーより先に `OTHER_ROOM_ACTIVE:` が返る）
- `leaveCurrentRoom` を無視して常に拒否する: ケース 8・9 が失敗する
- `leaveCurrentRoom` を無視して常に退出させる: ケース 10 が失敗する

## 今後の課題

1. forceJoin で抜けた旧部屋の他のメンバーへの退室通知（システムメッセージ、SSE の `member_update`、アクティビティ記録）が出ない。従来の強制参加の経路でも出ていなかったため、今回も同じ。通常の退出（`LeaveRoom` ハンドラー）は出しているので、揃えるなら別途対応する
2. `CreateRoom` ハンドラーは、GUEST の場合に先に退出してから部屋を作る。作成に失敗すると元の部屋だけ失う（今回の強制参加と同種の非原子性）。範囲外のため未対応
3. Postgres のデフォルトの分離レベル（READ COMMITTED）では、件数の取得と参加の追加が別のステートメントのため、最後の 1 枠に 2 人が同時に参加すると、両方入って定員を超える可能性が残る。対策するなら部屋の行ロックなどを検討する
4. 既存の稼働中の部屋は、`current_players` 列が実際より少ない値のまま残っている。参加判定は件数ベースなので影響はなく、参加・退出があれば正しい値に直る。列を直接表示している箇所（管理画面の部屋一覧、参加中の部屋を返す API）は、それまで 1 少なく表示されうる。活動のない部屋は 48 時間（`room-cleanup` の既定値）で自動解散されるため、時間とともに解消する
5. ブロック警告の確認後に参加する経路（`rooms.tmpl` の `confirmJoinWithBlock()`）は、409 を汎用メッセージ「参加に失敗しました」で表示する（従来と同じ。ROOM_FULL の文言は出ない）
