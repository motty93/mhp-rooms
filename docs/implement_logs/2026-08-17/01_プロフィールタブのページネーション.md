# プロフィール・ユーザー画面 タブのページネーション（Issue #47）

**実装時間**: 約 40 分（調査・設計 15 分 / 実装・検証 15 分 / 更新情報エントリ作成 10 分）

## 概要

プロフィール画面（自分: `/profile`、他ユーザー: `/users/{uuid}`）の「作成した部屋」「アクティビティ」タブに、20 件/ページのページネーションを追加しました。レコードが増えたときにタブ内のリストが際限なく伸びてレイアウトに影響する問題（Issue #47）を解消します。

## 設計判断

### 比較した案

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| **A. サーバー側ページネーション（採用）** | 件数取得 → ページ情報を組み立て → 部分テンプレートで描画。ページ送りは htmx で `#tab-content` を差し替え | 既存の部屋一覧（`/rooms`）と同じ方式で一貫性がある。取得件数が常に 20 件に抑えられる。JS 追加なし | 件数取得クエリが 1 本増える |
| B. クライアント側スライス | 全件（上限あり）取得して Alpine.js でページ分割 | 件数クエリ不要 | 表示しないデータも取得する。上限を超えると結局崩れる。既存方式と不一致 |
| C. 「もっと見る」/無限スクロール | `hx-swap="beforeend"` で追記 | 総件数不要でシンプル | Issue の要件は「ページネーション」。リストが伸び続けるためレイアウト問題の解決にならない |

### 採用案が破綻しうる変更
- タブ描画をサーバー側部分テンプレートから JSON API + クライアント描画へ移行した場合、ページ送り UI ごと作り直しになる
- タブやページ位置を URL に保持（ディープリンク）したくなった場合、`hx-push-url` と初期状態の復元処理が必要になる

### 動作の流れ

1. ページ描画時（`Profile` / `Show`）は 1 ページ目 20 件と総件数を取得し、`profile_rooms` / `user_profile_rooms` 部分テンプレートをそのまま初期表示に使う
2. ページ送りボタンは `hx-get="{BaseURL}?page=N"` で同じタブ API を呼び、`#tab-content` を差し替える。`hx-swap="innerHTML show:#profile-tabs:top"` でタブカードの先頭までスクロール
3. `BaseURL` は API ハンドラーでは `r.URL.Path`（`/api/profile/rooms`、`/api/users/{id}/rooms` など）をそのまま使うため、自分/他ユーザーどちらのルートでも正しいリンクになる
4. アクティビティは従来どおり「過去 2 週間」の範囲を維持しつつ、フィルタを Go 側の後処理から SQL の `created_at > ?` に移し、同じ条件で件数を取得する

## 特に注意した点・工夫した点

- **既存仕様の維持**: アクティビティの 2 週間ウィンドウ（`docs/implement_logs/2025-09-17/04` で導入）は意図的な仕様のため維持。従来の「100 件取得 → Go でフィルタ → 20 件で切り捨て」を DB 側条件に置き換え、切り捨てで見えなくなっていた分もページ送りで辿れるようにした
- **DRY**: 作成した部屋の取得は 5 箇所（自分ページ初期表示・自分タブ・他ユーザーページ初期表示・他ユーザー JSON API・他ユーザータブ）で同じ処理だったため `BaseHandler.hostedRoomsPage` に集約。page クエリの解釈も部屋一覧と共通化
- **テンプレートの重複解消**: `profile.tmpl` / `user_profile.tmpl` に部分テンプレートと同内容のマークアップが直書きされていた（約 60 行 × 2）ため、部分テンプレート呼び出しに置き換え。今後リスト表示を変更するときの修正箇所が 1 つになった
- **モバイル対応**: ページ番号は「先頭・末尾・現在±1」を表示し、先頭・末尾・省略記号は `hidden sm:inline-flex` でモバイルでは非表示（狭い幅でも折り返さない）
- **ID 使用ルール**: リンク・API パスはすべて主キー `User.ID` / `Room.ID` を使用（`SupabaseUserID` 不使用）
- **環境別分岐なし**: 開発・本番で同じロジック
