# 部屋詳細 キック機能（Issue #11）

**実装時間**: 約 30 分（調査・設計 15 分 / 実装・検証 15 分、16:15〜16:45 頃）

## 概要

部屋のホストがメンバーを部屋から退出させられる「キック」機能を実装しました。部屋詳細のメンバーをクリックすると操作メニュー（プロフィール / 通報 / キック）が開き、キックは確認モーダルを経て実行されます。退出させられたユーザーは同じ部屋に再参加できず、本人の画面には通知が出て部屋一覧へ戻されます。通報を送信した直後は、Issue の指定どおりそのままキック確認へ続けられます。

## 設計判断

### メニューの見せ方
Issue では「ツールチップ」となっていましたが、メンバー一覧は `overflow-y-auto` のコンテナ内にあり、絶対配置のポップオーバーだと下端で切れる恐れがあるため、**行の直下にインライン展開する操作メニュー**にしました。モバイル幅でもそのまま使え、位置計算も不要です。

### キック済みユーザーの扱い
`room_members.status` に `kicked` を追加し、退出処理は既存の `LeaveRoom` と同じ流れ（status 変更・人数減算・ログ）を `removeMember` に共通化して `left` / `kicked` を切り替えるだけにしました。`JoinRoom` は `kicked` 行があれば `KICKED:` エラーを返し、ハンドラーが 403 + `{"error":"KICKED","message":…}` に変換します（`ALREADY_JOINED` / `OTHER_ROOM_ACTIVE` と同じ流儀）。

### 本人への通知
Job のような別プロセスではなくサーバー内なので、既存の SSE hub から `member_kicked` イベント（対象の `user_id` / `supabase_user_id`）を配信し、本人のクライアントだけが `alert` → `/rooms` へ遷移します。他のクライアントには従来どおり `system_message` と `member_update` でメンバー一覧が更新されます。

### 採用案が破綻しうる変更
- キックの取り消し（再参加許可）が必要になったら、`kicked` → `left` に戻す API と UI が必要
- ブロック機能（#12）を本格実装する際、「キック時にブロックも行う」導線を足すなら、キックモーダルにチェックボックスを追加する形になる
- SSE を別サービス（`huntershub-sse`）に分離した場合、`member_kicked` の配信経路が変わる（現状はメインサービス内の hub）

## 特に注意した点・工夫した点

- **権限チェックはサーバー側で完結**: ホスト以外・自分自身・ホスト自身へのキックは API が拒否。UI の表示制御はあくまで補助
- **既存の退出フローとの共通化**: `removeMember(roomID, userID, status, action)` に一本化し、退出/キックで人数更新やログの挙動がずれないようにした
- **ID 使用ルール**: API のリクエストボディとプロフィールリンクは主キー `User.ID`。クライアント側の「自分かどうか」判定は既存コードに合わせて auth ストアの Supabase ID と比較（URL/API には使わない）
- **通報 → キックの導線**: 通報モーダルは既存コンポーネントをそのまま部屋詳細に載せ、成功時のカスタムイベントだけ追加。ホスト以外が通報した場合は何も起きない
- **JavaScript の構文検証**: Go テンプレート内の JS はブラウザで開くまで壊れに気づきにくいため、描画結果から `<script>` を抜き出して `node --check` にかけるテストを追加（JSON-LD は除外）
- **環境別分岐なし**: 開発・本番で同じロジック（ルーティングの認証有無分岐は既存構造に従っただけ）
