# 放置された部屋の自動削除（Issue #167）

**実装時間**: 約 60 分（調査・設計 20 分 / 実装 25 分 / Turso での検証・ドキュメント 15 分、10:20〜11:00 頃）

## 概要

最後の活動から一定時間（既定 **48 時間**）経過しても動きがない募集中の部屋を、Cloud Run Job `room-cleanup` で自動的に解散する仕組みを実装しました。Cloud Scheduler から 1 時間ごとに実行します。自動解散された部屋はホストのプロフィール「作成した部屋」で「自動削除」ラベルと理由が表示され、アクティビティにも記録されます。

## 設計判断

### ユーザーと決めたこと
- しきい値: **48 時間**（環境変数 `ROOM_INACTIVE_HOURS` で変更可能）
- 実行方式: **Cloud Run Job + Cloud Scheduler**（Issue の想定どおり。サーバー内 goroutine 案は Cloud Run の複数インスタンスで重複実行しうる・アクセスがないと動かないため不採用）

### 「非アクティブ」の定義
`is_active = true` の部屋のうち、しきい値以降に次のいずれもないもの:
- 作成・設定変更（`rooms.created_at` / `rooms.updated_at`。参加・退出時の人数更新でも `updated_at` は更新される）
- 参加・退出（`room_logs`）
- チャット（`room_messages`）

SSE の接続状況は DB に残らないため判定材料にしていません。`is_closed`（締め切り）の部屋も活動がなければ対象です。

### 「削除」の扱い
物理削除ではなく、ホストの「解散」と同じ `DismissRoom`（`is_active = false`・メンバー全員退出）を再利用。理由を残すために `rooms` に `dismissed_at` / `dismiss_reason`（`host` / `inactive`）を追加し、`room_logs` には `auto_dismiss`（操作ユーザーなし）を記録します。

### 採用案が破綻しうる変更
- 通知機能（#68）ができたら、プロフィール表示だけでなく通知に切り替える（Issue にも「一旦はユーザー画面で分かるようにする」とある）
- 「ホストの在席」を判定に使いたくなった場合、SSE 接続の最終時刻を DB に保存する仕組みが別途必要
- 部屋数が大きく増えた場合、`NOT EXISTS` サブクエリ + `datetime()` 正規化のコストが気になり始める（現状は数百件規模で 300ms 程度）

## 特に注意した点・工夫した点

### Turso（libSQL）の日時比較
検証中に、**libSQL では日時が文字列比較になり、格納値のタイムゾーン表記が混在（ローカル書き込み `+09:00` と Cloud Run の `+00:00`）すると大小判定を誤る**ことを一時テーブルで確認しました（4 ケース中 2 ケースで誤判定）。`FindInactiveRooms` では `datetime()` で UTC に正規化してから比較するようにし、同じ検証で全ケース正しくなることを確認しています。Postgres では素の比較で正しいため、`GetType()` で切り替えています。

`datetime()` が解釈できない値（ステージングのシードに `created_at` が空文字の部屋が 5 件あった）は NULL になり比較に一致しないため、**判断材料がない部屋は削除しない**安全側の挙動になります。

### 既存の解散フローとの共存
- `DismissRoom` を共通利用しつつ理由だけを追加したので、ホスト解散のログ・SSE 通知など既存挙動は変わりません
- 自動解散は SSE で「room_dismissed」を配信できません（Job から hub にアクセスできない）が、対象は 48 時間動きのない部屋なので接続中のクライアントは実質いない前提です
- 既に解散済みの部屋は対象外なので Job は冪等。Cloud Run Job の再試行（max-retries 1）でも二重処理になりません

### マイグレーション
`rooms` の追加カラムは GORM の AutoMigrate 対象で、Cloud Run のサービスは `RUN_MIGRATION=true` で起動時に自動適用されます。**Job（room-cleanup）はマイグレーションを実行しない**ため、サービスのデプロイ完了後に Job が動く順序になる Cloud Build の並列実行でも問題ありませんが、初回は Scheduler 作成前にサービスのデプロイ完了を確認してください。

### ID 使用ルール / 環境別分岐
- 部屋・ユーザーとも主キー `ID` のみ使用
- 開発・本番でロジックの分岐なし（DB 方言による比較式の切り替えのみ）

## テスト・動作確認

- `go build ./...` / `go vet ./...` / `gofmt -l`: 問題なし
- `go test ./...`: `cmd/room-cleanup`（環境変数の解釈）、`internal/handlers`（ステータスマッピング、注記の描画）とも ok
- ステージング DB（Turso）に対して `DRY_RUN=true` で実行: 48 時間以上放置の 21 件を検出、`duration_ms=279`。`created_at` 空の 5 件は除外
- 一時テーブル（ロールバック）で文字列比較と `datetime()` 比較の挙動差を確認
- `docker build -f cmd/room-cleanup/Dockerfile .` が成功し、コンテナが起動して環境変数を読み込むところまで確認
- `cloudbuild.yml` / `cloudbuild.stg.yml` の YAML 構文チェック、`prettier --check`、`go run cmd/generate_info/main.go` で更新情報のパースを確認
- 実際の削除（DRY_RUN なし）はステージング DB に対しても未実行。ステージングデプロイ後に `gcloud run jobs execute room-cleanup-stg --update-env-vars DRY_RUN=true --wait` → 問題なければ本実行、の順で確認する想定

## デプロイ時に必要な手作業

1. ステージング → 本番のデプロイ後、環境ごとに **Cloud Scheduler を作成**（`docs/deploy.md` の「放置部屋の自動削除」参照。Job を起動するサービスアカウントに `roles/run.invoker` が必要）
2. 初回は `DRY_RUN=true` で対象を確認してから本実行
